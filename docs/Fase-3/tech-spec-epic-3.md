## Overview

This document provides the technical specification for Epic 3: AI Study Plan Generation. This is the core "magic moment" of the application, where the user's unstructured syllabus and preferences are transformed into a structured, personalized study plan. This epic involves a more complex workflow than previous epics, orchestrating communication between the Next.js frontend, a dedicated FastAPI backend, and the external OpenAI service. The goal is to deliver an accurate, fast, and transparent plan generation experience.

## Objectives and Scope

**In-Scope:**
-   Parsing of uploaded syllabus text by an AI service to automatically identify topics.
-   A user-facing review step to confirm or edit the AI-extracted topics.
-   A fallback option for users to manually input topics if AI parsing fails.
-   The ability for users to customize their available study hours and set topic priorities.
-   Generation of a day-by-day study schedule (`study_sessions`) based on topics and user preferences.
-   Displaying a loading indicator during AI processing and clear error messages on failure.
-   Ensuring the entire plan generation process completes in under 10 seconds.

**Out-of-Scope:**
-   Real-time collaborative editing of the study plan.
-   Generation of quizzes or other study materials based on topics.
-   Support for syllabus formats other than plain text.

## System Architecture Alignment

This epic is a prime example of the separated frontend/backend architecture and demonstrates the rationale for having a dedicated FastAPI backend.

-   **Component Interaction:**
    1.  The **Next.js Frontend** captures the raw syllabus and user preferences.
    2.  It sends this data to the **FastAPI Backend**, which acts as a secure intermediary.
    3.  The **FastAPI Backend** constructs a prompt and communicates with the **OpenAI Service** to perform the heavy lifting of topic extraction and scheduling.
    4.  The results are stored in the **Supabase Database** (`syllabus_topics` and `study_sessions` tables).
-   **Centralized AI Logic:** As per the architectural decision, routing AI calls through the FastAPI backend prevents exposing the OpenAI API key to the client and creates an abstraction layer that allows for future changes to the AI provider without impacting the frontend.
-   **Data Model:** This epic populates the `syllabus_topics` and `study_sessions` tables, linking them back to the parent course.

## Detailed Design

### Services and Modules

| Service/Module | Responsibility | Owner |
| :--- | :--- | :--- |
| **Next.js Frontend** | Manages the "Guided Wizard" for plan generation, captures user input, and displays the final plan. | Frontend Team |
| **FastAPI Backend** | Exposes REST endpoints for AI tasks. Orchestrates calls to OpenAI. Contains the core scheduling logic. | Backend Team |
| **OpenAI Service** | External service (GPT-4) used to parse syllabus text and structure the initial plan. | OpenAI (Managed) |
| **Supabase Database** | Persists the final `syllabus_topics` and `study_sessions` generated by the workflow. | Supabase (Managed) |

### Data Models and Contracts

This epic populates the `syllabus_topics` and `study_sessions` tables based on the AI's output.

```sql
-- Populated by this epic
CREATE TABLE public.syllabus_topics ( ... );
CREATE TABLE public.study_sessions ( ... );
```
-   **Contract (FastAPI to OpenAI):** The backend will send a carefully constructed prompt to OpenAI, requesting a JSON object in return with a specific schema, e.g., `{ "topics": [{ "title": "...", "description": "..." }] }`.
-   **Contract (Backend to Frontend):** The FastAPI backend will expose a RESTful API.

### APIs and Interfaces

**FastAPI Backend Endpoints:**

1.  `POST /parse-syllabus`
    -   **Request Body:** `{ "syllabus_text": "..." }`
    -   **Response Body:** `{ "topics": [{ "title": "...", "description": "..." }] }`
    -   **Action:** Sends the syllabus to OpenAI for topic extraction and returns the structured result.

2.  `POST /generate-schedule`
    -   **Request Body:** `{ "course_id": 123, "exam_date": "2026-05-01", "topics": [...], "user_preferences": { "hours_per_week": 10 } }`
    -   **Response Body:** `{ "success": true, "session_count": 50 }`
    -   **Action:** Contains the scheduling logic. It calculates the distribution of study sessions and inserts them into the `study_sessions` table in Supabase.

### Workflows and Sequencing

The "Guided Wizard" flow described in the UX Design Specification is the primary workflow.

1.  **Syllabus Parsing:**
    -   Frontend sends syllabus text to the `/parse-syllabus` endpoint.
    -   Backend calls OpenAI, validates the response (checking for the correct JSON structure), and returns the topics to the frontend.
    -   Frontend displays the topics for user confirmation/editing.

2.  **Schedule Generation:**
    -   Frontend sends the final topic list, course ID, and user preferences to the `/generate-schedule` endpoint.
    -   Backend executes the scheduling algorithm (e.g., calculates total study hours needed, allocates hours per day, and creates `study_session` records for each topic).
    -   The backend performs a bulk insert of all `study_sessions` into the Supabase database.
    -   The backend returns a success message. The frontend then navigates to the dashboard, where the new sessions are visible.

## Non-Functional Requirements

### Performance

-   **CRITICAL:** The entire end-to-end plan generation process, from initial user submission to the final plan appearing, must take **less than 10 seconds**, as mandated by the PRD. This includes the round-trip to the OpenAI API.
-   The frontend must display a loading indicator throughout the process.

### Security

-   The OpenAI API key MUST be stored securely on the FastAPI backend (e.g., environment variable) and never exposed to the frontend.
-   The FastAPI backend must validate that the user making a request has ownership of the `course_id` being processed, likely by validating the user's JWT.

### Reliability/Availability

-   The system must handle failures from the OpenAI API gracefully (e.g., API is down, returns an error, or returns malformed JSON). In such cases, the backend should return a specific error code, and the frontend should display a user-friendly message, suggesting the manual input fallback.

### Observability

-   The FastAPI backend should log the duration of each call to the OpenAI API to monitor for performance degradation.
-   Any errors during parsing or scheduling should be logged with detailed context.

## Acceptance Criteria (Authoritative)

1.  **AC1:** The AI can parse unstructured syllabus text and identify a list of topics.
2.  **AC2:** The user can review, edit, and confirm the AI-extracted topics before plan generation.
3.  **AC3:** The user has an option to input topics manually if AI parsing is not desired or fails.
4.  **AC4:** The user can specify their study availability (e.g., hours per week).
5.  **AC5:** The system generates a complete study plan (a series of `study_sessions`) based on the topics and user preferences.
6.  **AC6:** A loading indicator is shown while the AI is processing.
7.  **AC7:** A clear error message is shown if plan generation fails for any reason.
8.  **AC8:** The end-to-end plan generation process completes in under 10 seconds.

## Risks, Assumptions, Open Questions

-   **Risk:** OpenAI API latency or variability could cause the generation to exceed the 10-second requirement.
    -   **Mitigation:** Implement prompt engineering best practices. Use smaller, faster models if feasible. Add timeouts to the API call.
-   **Risk:** The AI could "hallucinate" or produce inaccurate/irrelevant topics from the syllabus.
    -   **Mitigation:** The user confirmation step (AC2) is the primary mitigation. The prompt must be carefully designed to constrain the AI's output.
-   **Assumption:** A stateless FastAPI backend is sufficient. No complex session management is needed on the backend as authentication is handled via JWT.
-   **Question:** What is the exact structure of the prompt we will send to OpenAI?
    -   **Next Step:** This requires prototyping. A separate task should be created for "Prompt Engineering for Syllabus Parsing."

## Test Strategy Summary

-   **Unit Tests:**
    -   (Backend) Test the scheduling algorithm with various inputs (e.g., different numbers of topics, hours).
    -   (Backend) Test the OpenAI prompt construction logic.
-   **Integration Tests:**
    -   (Backend) Test the `/parse-syllabus` and `/generate-schedule` endpoints by mocking the OpenAI API and the database connection. This verifies the request/response contracts and core logic.
-   **E2E Tests:**
    -   Run the full "Guided Wizard" flow in a test environment. Use a canned syllabus text and mock the call to the FastAPI backend to control the test conditions and avoid actual OpenAI costs.
    -   Test the failure-handling path by having the mock backend return an error.
-   **Performance Tests:** Create a script to call the `/generate-schedule` endpoint repeatedly to measure its average response time and ensure it stays below the required threshold.
